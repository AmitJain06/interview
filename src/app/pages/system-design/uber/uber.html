Uber — Ride Hailing

The hardest proximity-search problem: match riders to nearby drivers in real time — notes from the Hello Interview breakdown (Ex-Meta Staff).

Full step-by-step notes for the video Design Uber w/ an Ex-Meta Staff Engineer: System Design Interview breakdown. Read in order: requirements → entities → API → working high-level design → deep dives (location store, matching consistency, surges, high availability). Every step embeds the actual whiteboard frame from the video next to a redrawn diagram — so you can watch the design improve one change at a time.

Delivery framework (identical to Top-K & Ticketmaster — reuse it every time)

  1. Requirements (~5 min) — functional (what) + non-functional (how well). Pick 3 FRs, quantify the NFRs.
  2. Core entities (~2-4 min) — Ride, Driver, Rider, Location. Bullet each; fill the schema later.
  3. API (~5 min) — the contract. Implement the endpoints and the FRs are done.
  4. High-level design (~10-15 min) — simplest system satisfying functional reqs. Deliberately imperfect.
  5. Deep dives — return to the NFR list and attack what's missing. Where senior/staff earn the offer.
Golden rule from the video: skip back-of-envelope estimate math up front — only compute when a number can change a design decision. Then make sure every deep dive ≤1 NFR.
  • FR1 — get a fare estimate: rider inputs start + destination → app returns ETA and price. The video marks out of scope: multiple car types / ratings / scheduled rides. One car type (UberX), one estimate.
  • FR2 — request a ride: from that estimate, request a ride and get matched, in real time, to a nearby available driver.
  • FR3 — driver accepts / denies then navigates: driver accepts or denies; once matched, navigates to the pickup location and then to the destination.
  • NFR1 — low-latency MATCHING: < 1 min to match or fail. Care about latency on the hot path only, and quantify it. Failure = tell the rider "no available drivers in the area". This picks the location store + the matching deep dives.
  • NFR2 — STRONG consistency OF MATCHING (CAP choice). A ride is matched 1:1 to a driver — never two drivers to one ride, never two rides to one driver. This is the $ cost of CAP here and drives the distributed-lock deep dive.
  • NFR3 — high availability EVERYTHING OUTSIDE matching. Serve 24/7; minimize downtime for estimates, requests, navigation, profile. Matching itself trades availability for exactness.
  • NFR4 — high throughput in SURGES. Stadiums / NYE / Taylor-Swift-out = hundreds of thousands of requests within one region. That number names the queue deep dive.
CAP takeaway (say this unprompted): consistency for matching + availability for everything else. Same "stale reads, exact writes" asymmetry you already know from the Ticketmaster booking lock.
  • Ride — id, riderId, fare, eta, source, destination, status (fare_estimated → requested → matched → picked_up → dropped_off).
  • Driver — id + metadata (car, plate, photo, …) and crucially status: available | in_ride | offline | request_sent.
  • Rider — id + metadata (location, payment, …). Dots mean "don't design the profile now".
  • Location — driverId → (lat, lng), the most up-to-date current locations only. Lives apart from the primary DB specifically so proximity queries are cheap.
  • POST /ride/fare-estimate — body {{ '{' }} source, destination {{ '}' }} → {{ '{' }} rideId, eta, price {{ '}' }}. Creates a PARTIAL Ride row (status fare_estimated). Abandoned estimates are analytics gold — "people priced this ride but never booked it".
  • PATCH /ride/{rideId}/request — async: rider asked to match. Returns 200/202 since matching takes up to a minute off the critical path.
  • PUT /driver/location — every ~5 s, the driver app calls with driverId, lat, lng. (Candidates commonly miss it in the API section — fine, the API grows as you design.)
  • PATCH /ride/{rideId}/accept — body {{ '{' }} accept: true/false {{ '}' }}; the driver answers the push. Update ride status + set driver ID.
  • PATCH /ride/{rideId}/update — body {{ '{' }} picked_up | dropped_off {{ '}' }}; respond with the next lat/lng to navigate to, or null when done.
Security note (the interviewer checks): never put user/driver IDs in the request body — identity comes from the session/JWT header. Otherwise any user can request a ride on someone else's behalf.
  • Why an API gateway: load-balances, routes each request to the right microservice, and does authn, TLS termination, rate limiting. Write the bullets; don't over-explain — it's not the meatiest part.
  • Fare model: black-box an ML model OR simplify to "fare ≈ ETA × rate". Either is fine — the video simplifies out loud.
  • Ride row written NOW with status fare_estimated — before any request/match happens. Every subsequent API just updates this one row.
  • Ride Matching service — separate from Ride service because matching is computationally expensive AND asynchronous (each attempt waits ~10 s for a driver). That also isolates its failures.
  • Location DB — stores only current driver locations so matching can ask "who is within 1-2-3 miles of the rider?" Add the get-status filter to skip offline / in-ride drivers.
  • Notification service — black-box (it's its own interview question); native push to the driver device: "Accept this ride?"
  • Driver accept → hits the ride endpoint → update status + ride.driver_id → matched. Driver update → picked_up / dropped_off → the service returns the next lat/lng to navigate to (or null when done).
  • Location updates flow continuously: driver app → (PUT /driver/location) → location service → Location DB — so appetite loops every ~5 s.
  • Why B-tree lat/lng queries are bad: B-trees optimize 1D data; lat/lng is inherently 2D. Wide ranges scan many rows; a 20-mile radius means scanning a huge slice of the table. And Postgres realistically tops out ~2-4k TPS — 150-300x short.
  • A candidate lands on quadtree? Fine. Description: split a cell into 4 once it holds >K drivers; walk root→leaf to get neighbors. Great for uneven density + low write frequency. It needs an accompanying queue to batch 600k→~4k writes, which adds staleness + a full tree reindex per batch. Acceptable for mid; lead a senior toward the limit.
  • Redis + geohashing: the fit. Redis clusters handle 100k–1M ops/s, so no queue — events write DIRECTLY. Geohash = fixed-precision string keys; cheap to compute, trivial to index, and a write never rebalances a tree. That's why it wins for Uber's high-frequency updates despite uneven density.
  • Chooser rules (say them word-for-word): quadtree for UNEVEN density + LOW freq (Yelp — New York dense, Atlantic empty); geohash for HIGH write freq no matter the density (Uber, we re-ping every 5s).
Dynamic location updates (600k → ~100k): make the client adaptive — skip pings while parked/driving/offline, pace by status and speed, and drop precision away from hot areas. Product-compatible and shows senior depth without new infra.
  • Invariant 1 (easy): one ride is handled by ONE matcher instance, so a local loop — while not match: next driver → notify → wait ~10s — satisfies it. No shared state needed.
  • Invariant 2 (hard): at concert-out, 100k riders share the same nearest drivers; the requests land on DIFFERENT servers, each ranking driver 1 first. A fix on a single box can't coordinate N instances.
  • Option A — status + cron: set driver.status=request_sent + updated_at; cron resets stale ones to available. Works, but a driver stays locked for TTL + up to the entire cron interval (5s + 60s) — too slow during surges. Good mid-level answer.
  • Option B — distributed lock with TTL (winner): SET driver:{id} = true in Redis with a 5-second TTL; every instance checks BEFORE sending. No response → the TTL auto-releases; the next reader sees no key and can retry. O(1), consistent, no cron job — the same idea as Ticketmaster's ticket lock.
Level check: cron = solid mid-level. TTL lock = senior+. Staff callouts: put the lock in DynamoDB as a driver_locks table with row TTLs (consolidation, HA, scales).
  • Why a queue, not just more matchers: each matcher holds a request for ~10s waiting on drivers. When 100k requests land at once you can't boot servers fast enough — queue + drain at a sustainable pace is the fix.
  • Partition by region (borough/city-granular) → no head-of-line blocking. A rural request that takes a whole minute can't delay Manhattan rides sitting behind it.
  • Crash-safety: a matcher acks only on completion. Die mid-match and the un-acked request gets re-pulled and re-matched. No lost rides.
  • HA outside matching: horizontally scale each service behind its own LB; DynamoDB (near-unbounded) + Redis (100k-1M ops/s) for stores; run the whole stack per region with primary-DB read replicas in each DC.
  • Say the comparison out loud: quadtree for Yelp-style uneven density with few updates; geohash when writes dominate (Uber), even though driver density is uneven.
  • Bonus (senior/staff): production Uber uses an H3 hexagon grid instead of squares so cell-center-to-edge distance is directionally uniform.
  • Smooth the write path — same as Top-K: Top-K = Kafka absorbs 700k views/s → Flink pre-aggregates. Uber = dynamic client pings (600k→~100k/s) + Redis absorbs writes directly. Rule: don't let every event touch the expensive store.
  • Consistency via TTL lock — same as Ticketmaster: TM = ticket lock (SET NX, TTL 10 min) one buyer/seat; Uber = driver lock (SET driver:{id}, TTL 5s) one request/driver. Rule: TTL auto-release beats cron cleanup every time.
  • Queue-as-admission-control — same as Ticketmaster: TM waiting queue for onsale stampede; Uber ride-request queue for stadium surges. Once again: queues as admission control, not storage.
  • The ONE new idea: 2D geospatial indexing — pick quadtree (uneven density, low write) vs geohash (high write) by the workload. That's the Uber-shaped muscle your other designs don't exercise.
  1. Requirements: 3 FRs (estimate → match → accept/navigate); NFRs = low-latency matching < 1 min · STRONG matching consistency (CAP) · HA outside matching · surge-proof throughput (~hundreds of thousands/region).
  2. Entities: Ride, Driver, Rider, Location — four nouns; Location is the special one (current positions only → fast proximity).
  3. API: POST /fare-estimate · PATCH /request · PUT /driver/location · PATCH /accept · PATCH /update. Identity from headers, never the body.
  4. HLD: gateway → Ride svc (maps) OR → Ride Matching svc (read Location DB → filter available → notify → wait for accept). Primary DB holds rides; Location DB holds current positions.
  5. Deep dive 1 (location store): Postgres lat/lng bad → PostGIS quadtree + queue okay → Redis geohash wins (handles 600k pings/s, no reindex).
  6. Deep dive 2 (consistency): per-ride loop + per-driver distributed lock (Redis TTL 5 s) — never two requests to one driver; no cron; same lock as Ticketmaster.
  7. Deep dive 3 (surge + HA): region-partitioned ride-request queue + horizontally scaled services + region-split stacks.
