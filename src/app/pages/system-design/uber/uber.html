Uber — Ride Hailing

Match riders with nearby drivers and track rides in real time.

  • Riders can request a ride, see a fare estimate, and track their driver.
  • Nearby drivers are matched to a rider within seconds.
  • Drivers can accept trips and push their location continuously.
  • Both parties can rate each other after the trip.
  • Low matching latency (sub-second) for a good user experience.
  • High availability — the system tolerates individual node failures.
  • Eventual consistency is fine for driver locations; matching must be strongly consistent to avoid double-booking.
  • Geospatial index (geohash or quadtree) to resolve nearby drivers from constant location pings.
  • Matching service pairs a rider with the best driver by distance and rating.
  • WebSockets push live driver locations and trip state to clients.
  • Event streaming (e.g., Kafka) carries trip and location events to analytics and pricing.
  • Surge pricing service adjusts fares from demand heat maps.
  • Shard by city or geohash region so each matcher handles a bounded area.
  • Keep driver locations in memory (Redis geospatial) rather than a relational store.
  • Throttle location pings and batch writes to keep write throughput manageable.
  • Use leader election per region so exactly one matcher owns a trip lifecycle.
