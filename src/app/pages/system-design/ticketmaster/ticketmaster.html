Ticketmaster — Ticket Booking

Search events, view seat maps, and never sell one ticket twice — notes from the Hello Interview breakdown with an Ex-Meta Staff Engineer.

Full step-by-step notes for the video System Design Interview: Design Ticketmaster w/ a Ex-Meta Staff Engineer. Read in order: requirements → entities → API → working HLD → deep dives (booking lock, search, caching, real-time seat map, surge queue). Every step embeds the actual whiteboard frame from the video next to a redrawn diagram — so you can watch the design improve one change at a time.

Delivery framework (identical to Top-K — reuse it every time)

  1. Requirements (~5 min) — functional (what) + non-functional (how well). 3 FRs only.
  2. Core entities (~2-4 min) — Event, Venue, Performer, Ticket. One SQL-vs-NoSQL sentence, move on.
  3. API (~5 min) — the contract: 2 reads + the reserve/confirm pair.
  4. High-level design (~10-15 min) — simplest system satisfying functional reqs. Deliberately imperfect.
  5. Deep dives — return to the NFR list and attack what's missing. Where senior/staff earn the offer.
Two goals the video writes on the board: satisfy functional requirements in the HLD; satisfy non-functional requirements in the deep dives. Every deep dive must trace back to an NFR — that's how you pick what to spend time on.
  • FR1 — Book tickets. The money path; everything else serves it.
  • FR2 — View an event. Details + venue + performer + seat map with available/booked seats.
  • FR3 — Search for events by term, location, type, date.
  • Out of scope (say it, stop): GDPR compliance, fault tolerance, auth. Naming them prevents scope creep later.
  • NFR1 — low-latency search → forces Elasticsearch later. (The presenter admits he forgot this one and went back to add it — editing your NFR list mid-interview is fine and even good.)
  • NFR2 — strong consistency for booking tickets → forces the Redis ticket lock. “One ticket, one owner, never sold twice.”
  • NFR3 — high availability for search + viewing events → cache layers, horizontal scaling.
  • NFR4 — read-heavy (100M DAU browse far more than they buy) → CDN + Redis cache “to hell”.
  • NFR5 — scalability for surges from popular events → virtual waiting queue (Taylor Swift onsale).
Math with a purpose: the video skips back-of-envelope estimations after NFRs on purpose — “most candidates compute QPS, say wow, big system, and learn nothing that informs the design. Math without a purpose.” Do math only where the result changes a decision (shard or not?), and do it in the HLD or deep dives.
  • Event — id, venueId, performerId, tickets[], name, description. The GET /event/{id} response assembles exactly this.
  • Venue — id, location, seatMap (the clickable map). Performer — id, “…who cares, the details there.”
  • Ticket — id, eventId, seat, price, userId, status: available | reserved | booked.
  • Storage choice in one breath: “consistency matters for tickets, relationships exist, I know Postgres well → Postgres.” Senior tip from the video: SQL-vs-NoSQL is an old, boring debate — state the qualities you need (ACID, transactions, joins) and note either could work.
  • View path: Event CRUD joins Postgres for event + venue + performer + tickets and returns the assembly.
  • Search path (v1, knowingly bad): a SQL … WHERE name LIKE '%term%' — the video says it “totally sucks, full DB scan”, but ships it anyway: working first, optimize in deep dives — the same golden rule as Top-K.
  • Booking path (v1): reserve → UPDATE tickets SET status='reserved' → 200; confirm → Stripe (async webhook) → UPDATE status='booked' + userId. Simple, correct… with a hole the next card fixes.
  1. The hole: user closes the laptop mid-payment → status stays 'reserved' FOREVER. Seat map (which queries available) never shows it again. NFR2 broken.
  2. Fix 1 — reserved_timestamp column: query “available, OR reserved-but-expired”. Works, but “your data model lies” — rows say reserved while actually expired, two sources of truth to keep consistent.
  3. Fix 2 — cron every 10 min: reset expired holds back to available. Mid-level passing answer — but a Δ gap: cron at 12:09 un-reserves a ticket that expired at 12:00 → it was really held 19 minutes.
  4. Fix 3 (optimal) — distributed lock: drop the DB write at reserve entirely. SET ticketlock:{ticketId} = userId NX EX 600. Seat map = query PG for available, then remove any ticketId present in the lock. TTL expiry auto-releases. No janitor.
  • Why distributed (not in-process memory): many Booking instances must share ONE consistent view of the lock — “this isn't a single machine.”
  • What if Redis dies? Bring a new one up; users holding locks from the last 10 min lost them → several users can reach payment for the same ticket. Postgres ACID still guarantees exactly one winner (“whoever submits first wins, the other gets an error”). Bad UX for a 10-min window, consistency never lost — “a conversation with the product team; I'd argue this is fine.”
  • Why Redis and not DB row locks: 100k fans → 100k held DB connections. Redis keys are O(1) and burn no DB connections; rows only change at confirm.
  • Why not Postgres: LIKE '%swift%' = full table scan, no relevance ranking, no typo tolerance. Different access pattern → different storage.
  • What ES buys: inverted index (term → documents), analyzed text (fuzzy/prefix), geospatial queries (quadtrees + geohashing) so term + location + date filter in one fast query. Single-digit-ms reads = NFR1 ✓.
  • “ES is NOT your primary store”: durability concerns + no complex transactions — the presenter used it as primary at his first startup “and learned the hard way”.
  • Sync options: (a) dual writes in app code — must handle partial failure (retry/rollback); (b) CDC: Postgres WAL → change stream → consumer updates ES. He draws CDC as a labeled arrow and says the stream+worker behind it is a fine abstraction for interviews.
  • Write-load nuance (say it): ES has per-second write limits (index updates per write) — heavy-update systems need a queue + batching. Here events/venues/performers change “tens, hundreds, maybe thousands a day — absolutely nothing”, so direct updates are fine.
  • Option 1 — OpenSearch node query cache: per-shard LRU cache of top ~10k queries; enable via config. “Quick, dirty, easy.”
  • Option 2 — Redis/Memcached: normalized search term → results; invalidate on updates.
  • Option 3 (his pick) — CDN: the system already has a CDN for static images; cache API responses 30-60s at the edge. Pros: wicked fast for popular events. Cons: many query-param permutations → few hits; lat/long precision kills overlap; personalization breaks it entirely.
  • View path cache: Redis key = eventId → {event, venue, performer}. No LFU/LRU needed if it all fits (or bound to upcoming events). Only tickets stay un-cached — dynamic.
  • The problem: seat map loads accurate… then 5 minutes later the user clicks a seat someone else already bought. For popular events this happens constantly — terrible UX.
  • Option 1 — long polling: client keeps an HTTP request open ~30-60s in a while loop; server answers only when a seat changes. “Super cheap, no new infrastructure — if users sit on the page 1-5 minutes, this is perfect.”
  • Option 2 — SSE (server-sent events): persistent connection, server pushes seat changes whenever it wants. Key comparison from the video: WebSockets are fully bidirectional; SSE is unidirectional server→client — “and that's all that we need here.”
  • Say it: “SSE between client ↔ API gateway ↔ Event CRUD; every status change (available/reserved/booked) pushes to the client. Implementation is out of scope, but that's the design.”
Interview pattern: the video leads with the CHEAPEST fix (long polling), names its valid range, then upgrades only when a stated fact (users stay longer) demands it. Same escalation discipline as Top-K's cache → cron step.
  • The failure without it: “they get to the page and it immediately goes black — 100,000 or a million people fighting for 10,000 to 100,000 seats.” Every NFR5 scenario (Taylor Swift, Super Bowl, World Cup).
  • Implementation: Redis sorted set as a priority queue by arrival time (or randomized for fairness — so users closest to the servers don't always win). Event-driven admission: every 100 seats booked → admit the next 100/1000.
  • Flow: user enters queue → “you're in the queue” → assigned a token/session → pulled off in batches → notified over the SAME SSE connection from card 9 → led to book. The components compose.
  • The closing quote to remember: “A simple solution, but a sophisticated solution… the best answer isn't the most technically complex — it solves the problem in a simple, creative way.”
  • Scaling chat (least interesting, but expected): managed API gateway with its own load balancers; every service horizontally scaled on CPU/memory; then the one real decision — sharding Postgres. Shard by eventId (majority of queries) or venueId (if geographic correlation is high). “No wrong answer — weigh the pros and cons with the interviewer.”
  • Level check (from the video): this design with the Redis lock already passes most mid-level interviews (“most mid-levels land on the cron job”); executed well it passes senior and probably staff/principal.
  • Close by checking every FR and NFR against the board. If both lists check out, you're done — stop drawing.
  • Cache the read path (same): Top-K = Redis read-through + cron pre-compute (TTL 30d). Ticketmaster = Redis cache-aside + CDN edge (TTL seconds-minutes) + ES node query cache. Rule that transfers: never let a user request trigger the expensive path.
  • Smooth the write path (same, different flavor): Top-K = Kafka absorbs 700k views/s → Flink pre-aggregates. Ticketmaster = waiting queue absorbs the onsale stampede → Booking trickles. Queue-as-admission-control instead of queue-as-storage.
  • Derived stores + async sync (same): Top-K's rollup tables ↔ Ticketmaster's ES index. Rule that transfers: one source of truth, everything else rebuildable.
  • The ONE new idea: Top-K tolerates ~1-min staleness; booking demands strong consistency — Redis ticket lock (SET NX, TTL 10 min) serializes ownership. That asymmetry (stale reads, exact writes) is the senior signal.
  1. Requirements: book / view / search; NFRs = low-latency search, strong booking consistency, HA for reads, read-heavy (100M DAU), surge-proof.
  2. Entities: Event, Venue, Performer, Ticket (status available | reserved | booked) → Postgres, stated via qualities not the SQL-vs-NoSQL debate.
  3. API: GET /event/{id}, GET /search?term&location&type&date, POST /booking/reserve, PUT /booking/confirm (Stripe webhook).
  4. HLD: gateway (authn · rate limit · routing) → Search svc → ES; Event CRUD → PG; Booking → PG + Ticket Lock + Stripe; working but knowingly slow.
  5. Deep dives: distributed lock with TTL (fix the forever-hold), ES inverted index + CDC, CDN + Redis query caching, SSE seat updates, virtual waiting queue for surges.
  6. Close: check every FR + NFR against the board; sharding by eventId/venueId as the offered follow-up.
