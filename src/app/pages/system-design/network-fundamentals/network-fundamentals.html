Network Fundamentals

Core networking concepts for System Design interviews — layered cake, key protocols, load balancing and failure handling.

Notes built from the video Networking Essentials for System Design Interviews (Hello Interview, Ex-Meta Senior Manager — video file in /public), following my own study notes as the outline. The video has four parts:

  1. The basics — the OSI model: how networking works fundamentally as a layered cake.
  2. Each layer, at the protocol level — IP → TCP/UDP → HTTP → REST/GraphQL/gRPC → SSE → WebSockets → WebRTC, plus when to use which.
  3. Load balancing — where networking and scaling meet (client-side vs dedicated, Layer 4 vs Layer 7).
  4. Deep dives — regionalization, timeouts / backoff / retries, cascading failures and circuit breakers.
The golden defaults (remember these): TCP over UDP · REST over HTTP as the default API · Layer 7 load balancer as the default (Layer 4 for WebSockets / stateful connections) · timeouts + retries with exponential backoff + jitter · minimize statefulness in your design.
Two facts that drive every networking decision: (1) establishing a connection has a cost — a TCP connection needs a 3-way handshake (SYN → SYN-ACK → ACK), so lots of connections = lots of latency; (2) connections are stateful — a connection exists between "established" and "terminated", and that state is not cheap to set up or keep alive. Manage it deliberately.
  • Layers are abstractions — like calling open()/write() instead of moving voltages to disk. Each layer builds on the one below and stays oblivious to its details.
  • They build on one another: HTTP (L7) depends on a TCP connection (L4) being established; TCP (L4) depends on IP (L3) to route packets. Neither knows how the other's internals work.
  • Real example — an HTTP request: TCP 3-way handshake (SYN, SYN-ACK, ACK) → now a connection exists → client sends requests over that TCP stream → server responds. All the back-and-forth before your request even goes out is latency to account for in your design.
L3 Network · IP L4 Transport · TCP / UDP / QUIC L7 Application · HTTP, WebSockets, gRPC
  • Jobs of the network layer: give usable names (addresses) to nodes, and route — transfer data from one address to another.
  • IPv4 vs IPv6: we have run out of IPv4 addresses, not IPv6. Externally you typically use IPv4 (more compatible); internally IPv6 (more modern).
  • Public IPs — assigned by a central body; routers around the world are aware of them. Example: Apple owns every address starting with 18 (first 8 bits), so any packet to 18.x.x.x gets routed to Apple's routers.
  • Private IPs — you can assign nodes any name you like (e.g., 192.168.16.x, the special range for local networks); the only rules: you remember where they are and your routers know them. Purpose: guarantee no overlap with public addresses — you don't want a crate that sends "Google's" packets to your toaster.

Why it matters: to load balance across IP addresses you must know which hosts exist, where they are, and which ones to use — this bookkeeping is the seed of every service-discovery / load-balancing discussion later on this page.

TCP — the default: reliable delivery + ordering

  • Every packet gets a sequence number; sender and receiver can detect packets that are lost or out of order.
  • Lost packet: got packet 1 and 3 → assume 2 is missing → ask the sender to retransmit 2.
  • Out of order: got 5 right after 3 → wait for 4 before emitting 5 to the application layer above.
  • Guarantees are network-level only: TCP guarantees "the other host received the packet" — not "the data reached disk" on the other side. It is insight into the network, not absolute delivery (relevant when reasoning about CAP-theorem style failures).
  • Engineering cost: guarantees cost throughput and latency — a lost packet must be retransmitted before the stream continues; across far-apart hosts a retransmission round trip is expensive.

UDP — the machine gun: spray and pray

  • Fire-and-forget: send data, wish it a good voyage, hope it arrives. No ordering, no retransmission — great when latency is paramount and you can tolerate loss / out-of-order.
  • Video conference frame dropped? Don't go back to the host for that frame — drop it from the view, stabilize the audio, keep going. You might still tell the sender "you're dropping the connection, lower the bitrate" — but you don't care about any individual packet.
  • Classic UDP homes: multiplayer games, audio/video conferencing, live streaming — real-time, lossy applications.
  • Gotcha: browsers do not support UDP natively — for any browser client you need a TCP-based version alongside the UDP flow (e.g., mobile app).

Interview rule: your default is TCP. Move to UDP only when both hold — latency is critical and you can handle missing or out-of-order data. QUIC is a modern TCP replacement (higher performance, increasingly used for web) but looks like TCP in interviews — you can name-drop it, not design around it.
  • Most popular protocol — not just websites: even RPC systems run on HTTP. It is versatile and battle-tested over decades.
  • The verb tells intent — am I reading, updating, creating data? The path names what; the headers describe how/what I can accept; the body carries the payload.
  • Works on top of TCP — remember the layered cake: the HTTP layer depends on a TCP connection; TCP assumes IP can route packets — L7 builds on L4 builds on L3.
  • Content negotiation — the client says what it can receive (compressed? which encodings?) and the server replies what it actually gave you. This is what makes HTTP forward/backwards compatible as new versions roll out.
  • The name is misleading — "hypertext transport" sounds like web pages only, but HTTP is the base for APIs too: REST, SOAP, GraphQL — all ride on HTTP.
Example request you should be able to read aloud: GET /users/1 HTTP/1.1 + headers → 200 OK with a JSON body, plus headers telling you the content type and encoding. That is the entire HTTP contract — method, path, version, headers, status, body.
  • Think in resources + verbs, not function calls — /update-user is not RESTful (an action, not a resource). An update operation → PUT / PATCH on the thing being changed. Example: start a game → PATCH /games/1234 changing status from pending → running.
  • Returns JSON (typically) — data to render the resource the URL describes.
  • The default API choice in interviews — wide generality, everyone knows it, reasonably performant for most applications.
  • Trade-offs — there is overhead (URL + verb thinking) and, as we'll see next, REST can under-fetch or over-fetch when a single UI needs many resources.
  • Key idea: instead of "resources I tell you about", the client declares the view it wants to materialize; the server decides where every field comes from — one round-trip, minimal payload.
  • When it's genuinely valuable: (a) your front end changes constantly / you run experiments and requirements aren't firm; (b) multiple teams — a front-end team consuming several backends through one graph.
  • Costs: backend must resolve arbitrary query shapes (N+1 problems, resolver planning), caching gets harder, and one "handy" client can abuse the query cost budget.
  • In interviews: useful when the interviewer signals requirements will change quickly, or you need arbitrary query patterns — e.g., a newsfeed endpoint whose views aren't known up front. Otherwise REST is the default you should reach for.
  • Serialization is compact and efficient — no JSON key-value parsing per request; the compiler already knows the schema. gRPC services can be up to ~10× faster / more throughput than equivalent REST JSON endpoints.
  • Extra features built in: client-side load balancing, streaming, and rudimentary authentication.
  • Two real problems: (1) browsers don't support gRPC natively, so external clients can't talk to it directly; (2) binaries over the wire are hard for dev teams to debug.
  • Interview recommendation: gRPC is mostly an internal tool. Bring it up only when tightly optimizing performance — e.g., high-throughput interconnects between your own services — not for the client edge.
Best-of-both-worlds pattern: clients → HTTP/REST into your API server; your internal microservices ↔ microservices talk gRPC (or internal REST). External surface stays debuggable and browser-safe; internal connections stay fast.
  • HTTP: serves web pages and static content — the browser's native language.
  • REST: the JSON API every external client and mobile app understands — your default API gateway contract.
  • gRPC: where you own both ends and need speed (binary, streaming, client-side LB) — internal service-to-service calls.
  • GraphQL: when clients (or teams) need flexible, arbitrary data shapes over one endpoint instead of fixed resources.
  • In an interview diagram: say "clients hit an API gateway over REST; gateway fans out to microservices, and I'd use gRPC internally for the hottest path." Interviewers love that precision.
  • It's still HTTP — an HTTP response with headers like Transfer-Encoding: chunked; events separated by newlines. All existing proxies/gateways forward the stream, so you need no new infrastructure.
  • Different latency profile than a normal response: in a typical API you can't process the response until the whole body arrives; with SSE the first event arrives the moment the server writes it (chunked encoding), so a list of events spread over 10 seconds is processed as it streams.
  • Severed frequently: routers/proxies expect HTTP requests to finish in ~30–60 s and cut long connections. Clients such as EventSource auto-reconnect and can pass the ID of the last event received so nothing is missed between disconnect and reconnect — clunky, but it works.
  • Where it shines: short-lived UI updates (purchase status over ~15 s), notifications, live stock tickers, and — very modern — AI responses streaming tokens to the user as tokens are generated.
  • Rule of thumb: unidirectional push, moderate frequency → consider SSE before launching into heavy WebSocket infra.
  • Design its API in messages, not request/response — "receive ticker update" / "send subscribe", "send unsubscribe". You can still get a "subscription accepted" ack, but don't design a function-call style — that's what HTTP is for.
  • What "stateful" means here: a WebSocket connects one client to one specific server for the whole session. If a user stays connected for an hour, that server keeps that connection (socket, buffers, memory) alive for the whole hour. Rolling deployments kill sockets → users reconnect; a failed node drops all its connections; 1000s of users = 1000s of open connections = serious infrastructure.
  • Caveat — don't overuse: for a narrow feature ("show me a live bid on this page") prefer polling or SSE. WebSockets are powerful but demand infra; reserve them for genuinely high-frequency bidirectional needs: chat, realtime games, live dashboards, collaborative editing.
  • Interview pattern — push state to the edge: put a websocket gateway / notification service on the periphery; all users connect to it; internal (stateless) services call into it via RPC and it relays messages down the sockets. Your internal design stays stateless; only the edge holds connections.
  • In interviews this also decides your load balancer: long-lived connections want Layer 4 load balancing (see below), not Layer 7.
Chat vs WebRTC (common confusion): text chat is almost always WebSocket — messages must be ordered, reliably delivered and persisted server-side. WebRTC is for audio/video, where a dropped frame matters less than latency.
  • Why the dance: most clients won't accept inbound connections (security — you don't want random internet hosts connecting to your laptop). Signaling + STUN create a way for two firewalled/NAT'd clients to open a real peer-to-peer channel.
  • Why UDP: real-time media prefers latency over reliability — a dropped frame is skipped gracefully, while TCP head-of-line blocking would stall the call. This is the same "UDP for realtime/lossy" rule from the transport section.
  • Roles: signaling server — coordinates who connects to whom; STUN — "give me a usable address + punch the NAT"; TURN — relay when P2P can't be established (last resort).
  • Use it for: video/audio calling (Google Meet / Zoom style) — this is how they work; and collaborative editors / whiteboards, where peers exchange document updates and converge with CRDTs (conflict-free replicated data types).
  • Interview rule: avoid WebRTC unless the feature is literally audio/video calling (or a P2P collaborative editor). For plain chat you stay on WebSockets; for 95%+ of interview problems WebRTC is unnecessary.

  • Vertical scaling — bigger hosts (more memory/CPU). Modern hardware goes far (servers with terabytes of RAM exist), so start here — it's simpler and often enough.
  • Horizontal scaling — duplicate servers + balance requests and data between them. This is where the interview usually lands, and it forces you to solve load balancing.
  • Two ways to load balance: (a) client-side — the client knows all servers and picks one; (b) dedicated appliance — a device sits between clients and servers. Both are legitimate; the choice depends on who your clients are.
  • Why it's attractive: no extra hop — the request goes straight to the server that handles it, so you save the latency a dedicated LB adds.
  • The price: clients must learn about servers, so they tolerate update delays (a client won't instantly know a new/removed server), and you can't run sophisticated strategies (clients can't know server health/state).
  • DNS as client-side LB: resolving hellointerview.com returns a shuffled list of IPs; clients hit the first, fall back to the second, and so on — aggregate DNS traffic balances itself. But DNS is heavily cached: an IP-list change can take 5 minutes to a day to propagate — too slow for rapid scaling events or failovers.
  • Redis cluster: the client asks any known node for every master's address and then talks to the right shard directly — same pattern, no load balancer in the path.
  • Use when: you have few clients (classic internal microservices — great fit) or many clients that tolerate update delays. gRPC supports it out of the box — another reason gRPC shines internally.

Interview default: start with a Layer 7 load balancer (it's the default because it routes and terminates HTTPS for you). The exception is WebSockets / stateful connections — those want a Layer 4 load balancer that moves whole connections instead of individual requests.

The problem: a US-based server serving a client from India pays ~20–80 ms of round-trip latency per request (the video's example: London ↔ New York is ~80 ms minimum, because the speed of light in fiber is finite). Lots of requests back and forth across an ocean = slow app, no matter how fast the code is.

1 · Split the problem by region — partition your data

  • Uber-style partition: a rider only requests drivers in the city they're in today. So the whole system can be replicated per region/city — each region is small, self-contained, and gives its users near-instant responses.
  • In reality you run data centers in regions that cluster nearby cities (East Coast, West Coast, EU, APAC…), not one server per city.
  • This only works when access is naturally regional. If a global product's users in Japan read posts written in the UK and commented on in the US, you can't neatly shard by location.

2 · Collocate data and processing

The classic mistake: put a web server in London (to be "close to the user") while the database stays in New York. Every request then does many short DB round-trips across the Atlantic before the response is built — the web-to-DB hop usually dwarfs the user-to-web hop. Keep your data and processing in the same region.

3 · Global data, three tools

  • Local / partitioned data — keep data in the region where it's most used (UK users access US data less often anyway, e.g., due to time zones).
  • Replication — write to your local region, then replicate asynchronously to others for fast reads. Cost: a lag window — a US post appears in Europe moments later. Fine for many products.
  • CDN (Content Delivery Network) — edge servers in hundreds of cities act like a cache: a recently requested front page is served instantly from the nearest edge point, saving the trip to your origin. Cache misses fall through to the origin server (the CDN becomes a proxy). A CDN also reduces backend load by absorbing repeated requests.

4 · Sharding by location — only when the boundary is fixed

  • Sharding data across shards per region works if every query stays inside one shard (location-bound access, e.g., "orders in my city").
  • It breaks when the region boundary isn't fixed or queries fan out across many shards — every cross-shard read adds latency and becomes a scatter-gather problem.
  • Practical recipe: cache the cacheable (CDN), replicate what must be global, and only shard by location for truly regional access patterns.

1 · Timeout — first, bound the wait

  • The worst case is a request that got acknowledged and then never answered — the client hangs forever. Always set a sensible timeout.
  • Too short is just as bad: a server that takes 4 s will fail against a 3 s timeout no matter how many times you retry. Timeouts must be long enough for your server, short enough to bound the wait.

2 · Retry — but naive retries cause a herd

  • Simple idea: a request fails → try again 5 s later. Repeating every fixed interval is naive because (a) the server probably hasn't changed, and (b) it synchronizes: if three clients all retry at the same moment against a server that handles 2 req/s, all three fail together — and then all three retry together forever.

3 · Exponential backoff + jitter = the gold standard

  • Exponential backoff: double the wait each failure — 2 s → 4 s → 8 s. The first retry stays fast (transient blips like a solar flare hitting a disk), but repeated failures imply something substantial is wrong, and the server gets half the load each round.
  • Jitter (randomness): even with backoff, synchronized clients still hit in lockstep. Randomize the delay — one retries at 2.5 s, another at 1.9 s, a third waits longer — so retries decouple and spread across the timeline.
  • Say it verbatim in interviews: "timeouts and retries with exponential backoff and jitter" — that's the gold standard for connections between servers.

The failure cascade

  1. Start healthy: Server A → Server B → Database. All fast.
  2. A trigger: an operator kicks off a DB snapshot for a backup → the database runs at ~50% efficiency and starts timing out B's queries.
  3. B retries politely: B has timeouts (good practice!) and retries its failing DB queries (also good practice!) — but those retries fail too, so B starts failing its own callers.
  4. A punishes B: A times out requests to B and retries them. Now B is overwhelmed by A's retries while it's already failing. B goes down.
  5. Restart B: B comes back — and instantly drowns again — because the DB is still slow and A is still hammering it. No party knows to stop; no one recovers.

The fix — a circuit breaker between A and B

  • Circuit breaker: like a house breaker that trips at too much current — software trips when failures exceed a threshold → the circuit "opens", and A fails fast (returns an error immediately, no traffic to B).
  • B finally gets a break from traffic, which gives the database a break — enough silence for someone to notice the snapshot and stop it, fix the DB, let it recover.
  • Self-healing: the breaker periodically resets automatically / lets a little test traffic through; once B responds in time again, the breaker closes and normal traffic resumes.
  • Operational bonus: alarm on tripped breakers so humans learn "something is egregiously wrong" instead of discovering B is down at 3 a.m. Failing fast and loud is safer than failing slowly.
Interview gold: name this pattern by name — circuit breakers turn a silent death spiral into a controlled, visible, recoverable outage. (Bonus points for senior+ questions: also mention timeouts, retries with backoff + jitter, bulkheads and graceful degradation.)
  1. OSI = a layered cake. Only layers 3 (Network/IP), 4 (Transport/TCP-UDP) and 7 (Application/HTTP) matter; layers build on each other — and connection setup costs latency (3-way handshake) plus state.
  2. L3 — IP: IPv4 (4 bytes, we ran out) vs IPv6 (16 bytes). Public IPs for the internet-facing edge (API gateway, load balancers); private IPs for internal microservices.
  3. L4 — Transport: TCP = default (reliable, ordered, but costs throughput/latency); UDP = when latency is paramount and loss is tolerable (A/V, games); QUIC = modern TCP lookalike.
  4. L7 — Application protocols: HTTP (base), REST (default API — verbs + resources), GraphQL (flexible data shapes), gRPC (fast binary, internal only), SSE (server→client push, one-way), WebSocket (bidirectional push, stateful), WebRTC (P2P audio/video over UDP).
  5. Load balancing: horizontal scaling creates it. Client-side (Redis, DNS — few clients or tolerant of slow updates) vs dedicated (health checks + round-robin / least-connections). Default LB: Layer 7; Layer 4 for WebSockets/stateful.
  6. Regionalization: partition data by region when access is regional (Uber), keep data+processing collocated, replicate what's global, CDN-cache the cacheable; shard by location only when queries stay regional.
  7. Failures: always timeout → retry with exponential backoff + jitter (gold standard) → circuit breakers to stop cascading failures and self-heal.
Rapid-fire checklist: TCP not UDP · REST not GraphQL/gRPC by default · Layer 7 LB by default · timeouts + retries + backoff + jitter · collocate data & processing · stateful → edge; say all five and you've covered the networking core of almost any system design interview.
