Top-K YouTube Videos by Views

Stream-processing classic: precise Top-K over billions of videos and ~700k views/sec — notes from the Hello Interview breakdown (Ex-Meta).

Full step-by-step notes for the video Top-K System Design Interview Breakdown w/ Ex-Meta Senior Manager. Read in order: working-but-slow high-level design, then cache, pre-compute, write-path fix, full streaming design, optional deep dives. Every step embeds the actual whiteboard frame from the video (captions start with “Whiteboard”) next to a redrawn diagram — so you can watch the design improve one change at a time.

Delivery framework (use it every interview)

  1. Requirements (~5 min) — functional (what) + non-functional (how well, quantified, top 3-5).
  2. Entities (~2 min) — nouns: Video, View, Window. Keep it fast here.
  3. API (~5 min) — the contract. Implement the API and you are done.
  4. High-level design (~10-15 min) — simplest system satisfying functional reqs only.
  5. Deep dives — layer NFRs on: latency, scale, freshness.
Golden rule: start working, not optimal. Easier to optimize a working system than to fix an optimal-but-broken one.
  • FR1 — ingest every view event from an upstream Kafka video_views topic. You design only the Top-K feature, not all of YouTube.
  • FR2 — precise Top-K (K up to 1000), all-time. The unchanging leaderboard (Gangnam Style test).
  • FR3 — precise Top-K for tumbling windows: 1h, 1d, 1 week (7 days), 1 month (28 days). Fixed 7/28-day blocks — no calendaring.
  • Below the line: arbitrary ranges (Oct 2019?), true sliding windows, per-language/creator filters. Name them, defer them.
  • NFR1 — write freshness ~1 min (event happens to counted in Top-K). Covers retries, congestion, out-of-order events; justifies cache TTL + stale-on-failure later.
  • NFR2 — read latency tens of ms (single-digit on cache hit). Forces pre-computation — per-request compute can never hit this.
  • NFR3 — cardinality: billions of videos (TBD). Cannot sort per request; must pre-compute.
  • NFR4 — write scale: hundreds of thousands to ~700k views/sec (TBD). The hardest dimension — flag it early.
  • NFR5 — precise results, no approximation. Precise is easier to design well; Count-Min Sketch is a senior/staff deep dive only.
Phrasing tip: “low-latency Top-K reads in tens of ms” beats “system should be low latency”. Quantify + scope to the hot path. Pick 3-5 only.
  • Tumbling: last week = Sunday-to-Sunday of prior week. Query = SUM(views) WHERE ts BETWEEN start AND end. One cron run per window type per hour.
  • Sliding: last 7 days from this second — range moves as time moves. Needs add-new/subtract-expired maintenance (deep dive).
  • Say: “I'll assume tumbling (week = 7d, month = 28d). If you want true sliding I'll add minute tables + Flink sliding windows later.”
  • Video (videoId), View (videoId + ts, one Kafka message), Window (all-time | 1h | 1d | 7d | 28d).
  • REST: GET /views/top-k?window=7d&k=50 returns sorted [{{ '{' }} videoId, views {{ '}' }}] desc. K 1-1000, so no pagination (worst case = KBs).
  • No write API — views arrive via the assumed Kafka topic. State the assumption out loud.
  • Write path: one UPDATE per view (views = views + 1). Simple, correct — and the bottleneck (hot rows for viral videos, index churn).
  • Read path: fast ONLY because of the INDEX on views (sorted list → grab first K). Without it Postgres scans + sorts everything.
  • Say out loud: “I know this doesn't scale — one box, hot-row contention, and it can't answer window queries. That's intentional: working first, optimize in deep dives.” Juniors: start here. Staff: you may start one step ahead, but still narrate the trade-off.
  • Schema change: add ts_hour (round each view down to its hour). Row count grows (one row per video per active hour) but history is now distinguishable — last month vs last year no longer “bungled together”.
  • Index change: drop reliance on INDEX on views (useless for grouped sums); add INDEX on timestamp so the planner can at least skip out-of-window rows. Still must read EVERY in-window row + aggregate + sort.
  • Why hourly (not per-view, not per-day): per-view rows = unbounded explosion; per-day rows can't serve hour windows. Hourly is the granularity that serves 1h/1d/7d/28d.
  • Interview line: “This satisfies the functional requirement but violates NFR2 (tens of ms). That gap is exactly what my deep dives close.”
  • Why cron beats lazy caching: distributed systems reward predictability. Scheduled ~1 query/hour vs thousands of live RPS hitting a minutes-long query on every rollover.
  • Failure rule (say this unprompted): on cron failure, serve slightly-stale cache + alert + retry with backoff. NEVER fall through to the DB — one scheduled QPH becoming thousands of live QPS melts the DB (thundering herd).
  • NFR link: the 1-min freshness budget + tens-of-ms read NFR jointly force this: users accept ≤1h-old data; stale-by-2h on rare failure is within spirit.
  • Why not just “more Postgres”: every view is an UPDATE on a hot row (viral videos serialize on row locks) plus index churn. Batching in Flink removes per-view DB writes entirely.
  • Rollups: Flink emits VideoViewsHour; Day = SUM of 24 hourly rows, Month = SUM of 28×24. Index on (timestamp, views). Cron queries small tables only.
  • Say: “Reads are safe behind cache, but every view is a write I can't cache away — so the write path must change from per-view UPDATEs to streaming pre-aggregation.”
  1. Postgres alone: correct, 70x over write limit, window queries scan TBs.
  2. + Redis read-through: fast hits, catastrophic predictable misses.
  3. + Cron pre-compute: predictable ms reads, stale-on-failure, no DB fallthrough.
  4. + Flink aggregation: DB stays small, cron queries stay fast. Done.
  • Sliding steering line: “Tumbling covers hour/day/week/month blocks. True sliding needs minute tables + Flink sliding windows — want me to go deeper there, or stay with tumbling?” Let the interviewer steer.
  • CMS positioning: “My NFR5 says precise. If you want, CMS + a size-K min-heap trades bounded over-count for far less memory — but most interviewers don't expect it below senior/staff.”
  1. Requirements: precise Top-K ≤1000, all-time + tumbling 1h/1d/7d/28d; freshness ~1 min; reads tens of ms; billions of videos; ~700k views/s; no approximation.
  2. API: one endpoint GET /views/top-k?window&k, sorted, KBs — no write API (Kafka assumption), no pagination.
  3. HLD: Kafka topic (assumed) → consumer → Postgres(videoId, views, ts_hour); window query = filter + GROUP BY + SUM + sort + LIMIT k. Functional but slow.
  4. Read fix: Redis (window key, TTL 30d) → cron pre-compute (predictable); stale-on-failure, never DB fallthrough.
  5. Write fix: Flink hourly tumbling aggregation (100s GB → 10s GB → KBs); Day/Month = rollups; cron reads small tables.
  6. Below the line: sliding windows, arbitrary ranges, filters, CMS — named, deferred, offered as follow-ups.
