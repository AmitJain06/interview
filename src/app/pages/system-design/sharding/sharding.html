Database Sharding

Split one database across many nodes so writes, reads and storage scale horizontally.

What a shard actually is

  • Each shard is a standalone database — its own CPU, memory, storage and connection pool.
  • It stores one subset of the data; all shards together form the full dataset.
  • Add a shard → storage, read and write throughput scale horizontally.
  • New problems it creates: choosing a shard key, routing queries, hot shards, rebalancing, node failures, cross-shard queries and transactions.

The shard key is the field we group data by — all rows for one key value live on the same shard. A good key satisfies the video's three rules (the two extra refinements below come from the same logic).

Every read is a profile or a timeline for one user, so the shard key is the user_id – it satisfies every rule above.

  • Choose user_id (hash) – hundreds of millions of distinct values, evenly spread, and it is the field every hot READ filters on, so one query maps to one shard.
  • Avoid tweet_id – it auto-increments and grows forever; live tweets all flood the newest shard, leaving the rest idle.
  • Avoid created_at / date – monotonic and time-bucketed, so "today" becomes a single hot shard, and old data roams idle.
  • Avoid country / region – low cardinality with huge skew (say the US is 30%+ of users), so a couple of shards go hot, and most sit near-empty.
  • Avoid email – cardinality is great but it can change, and hot queries (timeline, profile) don't filter by email, so reads scatter-gather.
Same logic, second example: an e-commerce app whose hottest flow is one order (create, review, track) shards by order_id — the key always follows the hottest single-entity query.

Strategy A — range-based: split the key into ranges

  • How: split the key into simple ranges; each range lives on its shard.
  • Pain point 1: early days (1M users) → only the first range holds data and load; the rest sit empty.
  • Pain point 2: auto-increment IDs grow forever → all active (new) users land on the last range → that shard goes hot.
  • When it's fine: data that naturally falls into clean ranges and grows steadily — but you must split ranges before they get too big.

Strategy B — hash-based: hash(key) mod N — the industry default

  • How: hash the key, mod by the shard count — deterministically maps every key to one shard.
  • Win: solid, even distribution without thinking about the data.
  • Cost: add/remove a shard → "mod 3" becomes "mod 4" → almost everything re-maps → a full reshuffle (operational nightmare).

Consistent hashing — the ring that makes resharding cheap

  • Places the key on the ring, walks clockwise to the first shard — no modulo that breaks when N changes.
  • Virtual nodes sprinkle copies of each shard around the ring so loads stay balanced.
  • This is why "shard by user_id" is shorthand for hash-based + consistent hashing — the expected default in interviews.

Strategy C — directory-based: a lookup table

  • How: each read/write first asks the directory where the key lives, then queries that shard.
  • Win: total control — rebalance or relocate hot keys by rewriting the map, with no data-formula to fight.
  • Cost: +1 hop of latency on every request, and a directory outage means nobody knows where anything is (SPOF).
  • In interviews: almost never the right answer — keep hash + consistent hashing as your bread and butter.
  • Fix A — compound shard key: add a suffix before hashing — e.g. shard(user_id + post#) or shard(user_id + time) — so a single celebrity's data spreads across many shards.
  • Fix B — dedicated celebrity shard: detect high-traffic users, move them to their own (often bigger) shard and route them via a directory lookup; everyone else stays on plain hash + consistent hashing.
  • Most systems never need this — it exists for platforms with extreme outliers like a social media app.
  • First line of defence: choose a shard key aligned with the most common queries — then cross-shard queries simply happen less often.
  • Cache the result: run the expensive scatter-gather once, cache it (e.g. Redis, TTL ~5 min) — later reads are one cache hit. You trade a little staleness for latency, which is fine for feeds, leaderboards, trending pages.
  • Denormalize: store the related data together so the hot read stays on one shard — you pay on writes (write both copies) to win on reads.
  • Interview signal: constantly querying across all shards for a common use case means either the shard key is wrong, or you should cache/precompute, or denormalize. Cross-shard reads must be the exception, not the norm.
  • Golden rule: avoid cross-shard transactions — keep every row a transaction touches on one shard, whenever possible.
  • 2PC (two-phase commit): a coordinator asks all shards "ready?", waits for every YES, then says "commit". Correct in theory, slow and fragile in practice — one crash mid-way leaves locks that are hard to escape; production systems avoid it.
  • Saga pattern: chain small steps, each with a compensating action — if "credit Alice" fails, run "refund Bob $5". No global lock and no stuck state; this is the practical production choice.
  • Storage: 2.5 TB fits comfortably in one database → no shard needed; if we grew 10–100×, we would shard.
  • Writes: ~50k writes/s at peak exceeds one database's comfort zone → this is a real trigger to shard.
  • Reads: 100M DAU × several queries — even with read replicas, the read load must spread across shards.
  • The trap: candidates reflexively say "we shard by X". Saying "based on this math we don't need to shard yet" is often the more impressive answer — modern hardware goes a long way.

When a scaling NFR is unmet, walk the interviewer through these four moves (the video's closing framework):

  1. Propose a shard key from the access pattern. "Most queries are user-centric — profile, feed, followers — so I'd shard by user_id."
  2. Name the distribution strategy. "Hash user_id with consistent hashing to spread users evenly." (Senior+ can skip this — it's the default expectation. Junior/mid: say it explicitly.)
  3. Call out the trade-offs. "Global queries get expensive — we'd cache trending content or precompute it with a background job."
  4. Address growth. "Start with 10 shards for headroom; consistent hashing makes it easy to add shards or reshard when we need more capacity."
60-second recap: ceiling → justify with numbers → propose key (user_id) → hash + consistent hashing → trade-offs (hot spots, cross-shard reads, distributed transactions) → cache / compound keys / saga; start with room to grow.
