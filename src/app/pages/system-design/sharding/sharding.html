Database Sharding

Split one database across many nodes so writes,reads and storage scale horizontally.

A social app has ~100M users. A single Postgres instance sits at ~70% CPU at peak, holds ~4 TB and is one crash away from a total outage. Shard the database layer so it scales linearly.
  1. FR 1 - store ~100M user profiles; reads dominate, profiles change rarely.
  2. FR 2 - publish posts at ~5k writes/sec and return a user's posts in reverse-chronological order.
  3. FR 3 - point lookups by user_id (profile, posts) finish in < 50 ms.
  4. FR 4 - email login,and admin queries work without scanning every database node.
  5. FR 5 - a committed write survives the loss of a single node.
  1. NFR 1 - Scale: ~100M users, ~10B posts, ~500k read QPS,and ~50k write QPS.
  2. NFR 2 - Latency: p95 < 50 ms for user_id point lookups.
  3. NFR 3 - Availability: 99.99% (~52 min downtime per year).
  4. NFR 4 - Consistency: single-shard reads reflect committed writes; no lost commits on failover.
  5. NFR 5 - Storage: ~10 TB primary dataset,and growing; grows by adding nodes, not bigger disks.
  • User - user_id (PK), name, email,and created_at.
  • Post - post_id (PK), user_id,and created_at.
  • Follower - (user_id,follower_id) composite PK for the fan-out graph.

Shard key = user_id: every hot query filters by it first.
  • GET /v1/users/{id} - read a profile.
  • POST /v1/users/{id}/posts - publish a post,and return its post_id.
  • GET /v1/users/{id}/posts?cursor= - paginated recent posts.
  • POST /v1/auth/email - login by email; resolves email to user_id.

Satisfies FR 1-3 naively: the entire app runs on a single ACID database.

  • Trade-off: one relational instance gives free JOINs, transactions,and simple ops - but every NFR is capped by one machine's CPU, disk,and network.
  • Why it must change: at 100M users this box needs > 4 TB and ~50k writes/sec - far beyond one node's I/O budget.
  • Design change: nothing to split yet: app -> Postgres on one VM.
  • Improved: nothing needed at small scale - simple,and strongly consistent.
  • New problem: CPU, storage,and availability peak out together - one crash means 0% availability.

Triggers NFR 1 - scale: CPU at ~70%, disk at ~80%.

  • Trade-off: scale-up (32 vCPU,and 128 GB RAM, NVMe)vs scale-out(sharding). Scale-up,is trivially operable but hits a ceiling (~2-4 TB per box,and stays a single point of failure - picked as a stop-gap only.
  • Why add: cheapest win before committing to a data-model change.
  • Design change: before - default config; after - indexes on user_id,and created_at, PgBouncer connection pool,and work_mem tuning.
  • Improved: headroom to ~5-10M users; p95 stays < 50 ms.
  • New problem: the ceiling is real - writes,and storage cannot outgrow one machine,and a single box can never meet NFR 3(99.99%).

Triggers NFR 1 plus NFR 5 - scale,and storage: the vertical ceiling is reached.

  • Trade-off: hash(user_id)% N vs range sharding (by created_at or id ranges). Ranges give locality,and easy scans, but new data lands on one hot-tail shard; hashing spreads writes evenly - picked hash.
  • Why add: every hot query filters by user_id, so a user's rows live on exactly one shard -> single-shard reads stay fast.
  • Design change: before - one Postgres; after - 16 Postgres shards,with identical schema; the app computes shard = hash(user_id)% 16,and routes the query.
  • Improved: storage,and writes divide by 16 (~625 GB,and ~3k writes/sec per shard); point lookups stay p95 < 50 ms.
  • New problem: N is frozen - growing to 17 shards means rehashing nearly every key(a resharding storm,and email login now scatters across all shards.

Triggers NFR 5 - grow by adding nodes: modulo-N makes every resize a full migration.

  • Trade-off: modulo rehash (moves ~N/(N+1)of all data per resize)vs a consistent-hash ring - a 2^32 circle where each key lands on the first node clockwise of hash(key. Ring plus virtual nodes(each physical node owns hundreds of virtual arcs()gives even spread - picked ring.
  • Why add: the shard count must change as data grows, without rewriting the database world.
  • Design change: before - shard = hash(user_id)% 16; after - a shard-map service owns ring -> node ownership,and clients route through it.
  • Improved: 16 to 17 shards moves only ~1/17 of keys instead of 16/17; resharding becomes a background job instead of a freeze.
  • New problem: every node owns a different key range, so any non-key query fans out everywhere,and a hot key(celebrity account)pins one node,with all of its traffic.

Triggers NFR 3 plus FR 5 - availability: scaling is fixed, but any node crash is still a full-data outage.

  • Trade-off: async vs sync (quorum) replication. Async is fast but loses committed writes on a primary crash - unacceptable vs FR 5; picked synchronous commit to at least 1 replica.
  • Why add: NFR 3 demands 99.99%, impossible,with a single copy per shard.
  • Design change: before - 1 node per shard; after - 1 primary plus 2 replicas per shard; leader election(e.g., Patroni)promotes a replica,and the shard-map service points clients at the new primary.
  • Improved: availability ~99.99%; committed-write loss window ~0; replicas also absorb read fan-out.
  • New problem: 3x the nodes to operate,and email login still queries every shard - the read path needs a global lookup,the same way writes needed replication.

Triggers FR 4 - cross-shard reads: email login,and admin queries hit every node.

  • Trade-off: replicate hot keys(write N copies, read any copy)vs splitting the hot key itself(re-shard the celebrity's suffix by sub-key - powerful,but complex); picked hot-key replicas: cheap, reversible, reads scale.
  • Why add: one celebrity account can double a shard's traffic by itself.
  • Design change: before - one hot row = one shard = one bottleneck; after - a routing coordinator scatter-gathers queries in parallel(N shards, merge,and re-sort at the coordinator,and copies hot rows onto a few extra shards.
  • Improved: celebrity reads back under p95 < 50 ms; cross-shard lookups ~ slowest shard plus merge (~60-80 ms, acceptable for admin/login.
  • New problem: replicated hot rows need write-coordination,and fan-out grows linearly,with shard count - 100+ shards will blow the latency budget for login.

Triggers FR 4 - login by email: an email lookup has no user_id, so no shard key.

  • Trade-off: dedicated index table sharded by hash(email)- login becomes a point query on one index shard)vs a shared global index,in one DB(it would become a bottleneck itself); picked dedicated index
  • Why add: email to user_id is a rare but latency-critical lookup; fan-out to N shards cannot meet NFR 2.
  • Design change: before - user writes only hit the user shard; after - an outbox row is written transactionally,with the user,and a CDC pipeline,(e.g., Debezium to Kafka)applies it to the email-index shard - dual writes without blocking the user write.
  • Improved: login is one point lookup: p95 < 50 ms, zero fan-out.
  • New problem: outbox/CDC lag means the index is eventually consistent(a just-created account may take ~100 ms to appear),and true multi-shard transactions remain unsupported.

Triggers NFR 5 - safe growth: the chain now needs operational discipline, not new components.

  • Trade-off: build a routing proxy in-app(simpler,but couples business code to sharding)vs a dedicated proxy(Vitess-style: owns the shard map, rewrites queries,and hides shards from app code); picked dedicated proxy for separation of concerns.
  • Why add: resharding,and failover must be safe for engineers, not heroics.
  • Design change: before - app logic routes manually; after - proxy owns map plus routing; resharding = double-write old plus new shards, backfill, then cut over, one canary shard at a time.
  • Improved: shards added in days, not weeks; app code unchanged; failover handled centrally.
  • New problem(accepted residuals): cross-shard joins are banned(data model flattens them); no distributed transactions across shards(single-shard idempotent writes plus sagas instead); a single celebrity write storm still caps at one node's write rate(queue plus batch);and global analytics move to a warehouse/ES fed by the CDC pipeline.

  • 64 Postgres shards - each a primary plus 2 replicas; one per user_id hash-ring arc.
  • Routing proxy(Vitess-style) - owns the shard map, routes,and rewrites queries; app talks to it like one database.
  • CDC pipeline(Debezium to Kafka) - feeds the global email index,and warehouse/ES for analytics.
  • Hot-key replicas - celebrity rows copied to extra shards for read scale.
  • Data flow: POST /posts -> proxy -> user's shard primary -> sync commit -> replicas; login -> proxy -> email-index shard -> user_id -> user's shard; async jobs(outbox to CDC)keep auxiliary stores,in sync.
  • Storage: 10B posts times ~400 B ~ 4 TB,total ~5-10 TB with indexes.
  • Load: ~500k read QPS,and ~50k write QPS.
  • Over 64 shards ~ 160 GB,and ~8k reads/s,and ~800 writes/s per shard - comfortably under one Postgres box's limits.
  • Machines: 64 times 3 = 192 DB nodes plus ~8 proxy/front-end boxes(or a managed option like Vitess/Spanner).

Start with one database (v0). Vertical scaling buys time (v1), then hash-shard on user_id (v2). The modulo trap is a fixed N - switch to consistent hashing so resizing moves only ~1/N of the keys (v3. Harden availability,with a primary plus sync replicas per shard (v4. Cross-shard lookups,and hot keys get scatter-gather plus hot-key replicas(v5,and login by email gets a dedicated index fed by outbox plus CDC(v6. Operate it behind a Vitess-style routing proxy,and reshard via double-write plus canary backfill(v7.

Always name the alternatives: range vs hash, modulo vs ring, async vs sync replication,and single-writer vs multi-writer.
