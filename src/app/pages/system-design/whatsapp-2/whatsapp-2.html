WhatsApp — Chat App II

Step-by-step breakdown following the Hello Interview video transcript (Ex-Meta Senior Manager): start group chats → send/receive → media → read after offline. FRs below, design sections in progress.

Stefan's method in the video: "I open up the WhatsApp app — what do I see?" Requirements are the ~5-minute step; the FRs are deliberately small and then used as stepping stones for the high-level design — each one becomes exactly one design step later (v1 → v4). Everything heavy (latency, users, retention) belongs to the NFRs, not here.

  • FR1 — start group chats: the app opens on a list of chats, and for those chats to exist someone has to create them. Anyone can create a chat with a list of users; a group of two IS a 1:1 chat — one entity, no special-casing DM vs group. What we want to achieve: a user can create a 1:1 or group chat and it shows up in their chat list.
  • FR2 — send + receive messages between users: send once → the message fans out to every member; whenever another member sends, you receive it. The natural interviewer question — "do we support images/video/voice?" — becomes FR3 instead of growing FR2. What we want to achieve: two users in any chat can exchange messages reliably.
  • FR3 — media attachments: images, video and voice notes live inside messages, and uploads can be hundreds of MB. This single requirement later forces the S3 media path (HLD v3): a chat server shuttles kilobyte messages, not gigabyte blobs. What we want to achieve: attach and share media in a chat without breaking the message path.
  • FR4 — read messages after being offline: switch the phone off, come back, everything is still there. The video's key insight: a DEVICE goes offline, not a person — that is what creates the Client entity and per-device delivery. What we want to achieve: no message is lost while a recipient is offline; delivery resumes on reconnect.
  • Out of scope (the video's rule): calling, presence, spam and scraping sit in the out-of-scope box unless the interviewer pulls them in. If you're short on time, don't enumerate everything you're cutting — ask what the interviewer has in mind and move on.
Why these four: the transcript builds the HLD in exactly this order, one FR at a time — FR1 → chat + participant tables (v1) · FR2 → in-memory connection map (v2) · FR3 → S3 pre-signed media path (v3) · FR4 → messages + inbox with ACK-delete (v4).
  • NFR1 — low latency ≈ 500 ms delivery. The perceivable threshold: the difference between 100 ms and 500 ms is invisible in a chat app, so 500 ms is the real budget. This exact number comes back later to pick the routing mechanism between chat servers. What we want to achieve: the recipient sees a sent message within ~0.5 s.
  • NFR2 — guaranteed delivery. "It would be weird if I sent a message and they said they never got it." Server-side persistence + client ACKs make delivery provable, even when the recipient is offline at send time. What we want to achieve: no sent message is ever lost — delivery is retried until the device ACKs it.
  • NFR3 — high throughput: billions of users. WhatsApp serves a couple of billion users and many messages per user per day (~100B messages/day — the exact number is needed later for the storage budget). What we want to achieve: the design scales to ~2B users without a redesign; scaling is one deep dive, not a new problem.
  • NFR4 — data is toxic sludge (privacy). Don't keep messages longer than needed: either delete them or encrypt them "so even you can't read them". Drives the 30-day purge service — messages are kept at most ~30 days. What we want to achieve: nothing stays in the system past ~30 days.
  • NFR5 — fault tolerance. At this scale components fail constantly; no single-server failure may take the app down. What we want to achieve: losing any one server is invisible to users — they only re-connect, and nothing is lost.
CAP takeaway (say this unprompted): availability + eventual consistency for delivery — the inbox retries until ACK — with exactness kept only for the tiny transaction window. Chat is the opposite shape from Ticketmaster's booking lock: worth saying out loud.

Entities map 1:1 to tables. The CLIENT entity is the one candidates forget — "a person isn't offline, a device is offline" — and delivery ACKs are per-device, not per-person. Capture the important properties now; refine the schema later as the design evolves.

Say this out loud: five base tables (User · Chat · ChatParticipant · Message · Inbox) plus the Client entity candidates forget. The inbox row-per-recipient is the entire delivery guarantee.

Pick the transport first, name the commands second. Half of chat traffic is server → client, so the API is mostly WebSocket pushes, not HTTP responses.

How to explain the diagram aloud

  • Start with the transport, not the commands — "half of chat traffic is server → client, so the connection decides everything".
  • Walk the 3 questions in order: 500 ms latency ⇒ no polling · bidirectional ⇒ no SSE · no P2P/calls ⇒ no WebRTC ⇒ WebSocket.
  • Then name the commands straight off the board and say "this is just the start — I'll refine it as the design firms up."
  • Say why not REST unprompted — request/response can't push server → client; the WebSocket is what lets the server deliver.

Transport — reason to WebSockets in 3 steps (say them in order)

  • ① Latency-sensitive (500 ms, NFR1) → no polling: polling adds seconds of delay and server load.
  • ② Frequent bidirectional traffic → no SSE: SSE pushes only one way (server → client), so it can't carry sends.
  • ③ No peer-to-peer / media-call requirement → no WebRTC (calling is out of scope, per the FR section).
  • Why not REST: half of chat traffic is server → client events, and HTTP request/response only covers the client → server half — a RESTful API alone can't deliver a message.
  • Conclusion: a persistent WebSocket/TLS connection it is. (Real WhatsApp uses a plain TLS connection — same principle, less overhead.)

Iterate out loud: "this is just the scaffolding — I'll refine it as the design firms up." Never leave an obvious mistake sitting unacknowledged: the interviewer will assume you missed it even if you didn't.
  • Single chat server ON PURPOSE — the video's discipline: build the simplest thing that satisfies the FRs, then evolve it one problem at a time. Never jump straight to a distributed system.
  • The connection map is the whole trick: the server keeps client → WS (A→WS1 · B→WS2 · C→WS3). FR1 (createChat): A asks, the server adds B and C as participants (createChat internally implies modifyParticipants), then pushes chatUpdate to B and C over their live sockets.
  • FR2 (SendMessage): A sends "Hi All" once → the server fans out newMessage to B and C — a loop over the map. Sub-second, so NFR1 (500 ms) ✓.
  • DynamoDB (or any KV store): chat + chatParticipant tables. Composite PK (chatId, participantId) → "who's in this chat" · GSI on participantId → "which chats am I in" — both single-hop reads.
  • Why it's broken (say it yourself before the interviewer does): zero durability — B or C offline at send time sees nothing → NFR2 (guaranteed delivery) and FR4 (offline reads) fail. Media doesn't fit either — a 500 MB video would saturate the same pipe (FR3).
→ So we REDESIGN. This step lives only for the functional requirements — it breaks NFR2 (guaranteed delivery) and FR4 (offline reads) the moment anyone is offline. Let's fix that in the next step.
Checkpoint out loud: all 4 FRs plus 500 ms delivery hold on ONE node — "and I know exactly where it breaks: a user who's offline, then billions of users." → next steps fix durability (messages + inbox), then media, then scale.
  • The component change (one at a time, says the video): nothing is replaced — the single node and its connection map stay. We only add two tables and switch the send path from "loop and forget" to a write-then-push transaction. NFR1 (500 ms) still holds; NFR2 (guaranteed delivery) is now true too.
  • Messages table: id (PK) · contents · chatId · senderId · timestamp. The server stamps the time — not the client — so clocks stay consistent across senders, and the row outlives the connection.
  • Inbox table: recipientId · messageId — one row per undelivered copy. This row is the entire delivery guarantee: it lives until the client ACKs, which makes retries free (the sender doesn't care; on reconnect the server just drains un-acked rows).
  • The delivery contract: send = transact (messages + inbox) → if recipient online, push immediately → client ACKs → server deletes the inbox row. If recipient was offline, the message is already sitting in their inbox; on reconnect the server drains it → deliver → ACK → delete. Eventual, but guaranteed as long as the device connects.
  • ACKs are per device, not per chat: "B got it, C didn't" is a real state — that is why the inbox key is keyed by recipientId, and a row per recipient IS that state. This is the insight behind the Client entity: a person isn't offline, a device is offline.
Say this checkpoint out loud: "All FRs plus NFR1 (500 ms) and NFR2 (durable) now hold — even for users who reconnect later. But it still lives on ONE chat server. NFR3 (billions of users) does not — which is exactly where deep dives take over."
  • Why the naive version dies (two reasons — say both): ① DynamoDB is a row store, not a blob store — a 500 MB video blows the row-size budget and turns the DB into a CDN; ② the chat server saturates on gigabyte uploads while its real job is shuttling kilobyte messages — the 1:500 payload disparity is the smell. The fix is a component swap, not a rewrite.
  • Pre-signed URL handshake (5 steps, name them in order): ① Sender asks the chat server for an upload target · ② chat server (already authenticated/authenticated) gets an S3 pre-signed URL — auth is baked into the URL with a ~1 h TTL · ③ Sender uploads DIRECTLY to S3 (bytes never touch the chat server) · ④ the message body carries the URL, not the bytes · ⑤ recipients fetch from S3 when rendering.
  • The chat server stays the orchestrator, not the carrier: it authorizes the upload (is this sender in the chat? do they have permission?), issues an expiring, scoped URL ("you may PUT to this exact key, before this time"), then carries on with small messages. S3 handles the heavy lifting; the server handles the trust boundary.
  • You must also design EXPIRY: "or users get free Google Drive" — purge media shortly after every recipient has fetched it, with a ~30-day ceiling (the NFR4 "data is toxic sludge" safety net). Media outlives messages, so deletion has two levers: fetch-based and time-based.
Improvement over v2: nothing is replaced — the single node and its connection map, the messages + inbox tables, the ACK-delete policy all stay. The ONLY change is the media path: "the payload goes around the bottleneck, not through it."
