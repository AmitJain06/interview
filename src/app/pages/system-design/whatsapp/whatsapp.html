WhatsApp — Chat App

The stateful fan-out problem: ~100B messages/day over ~2B WebSocket connections, guaranteed delivery, and nothing stored past 30 days — notes from the Hello Interview breakdown (Ex-Meta Senior Manager).

Full step-by-step notes for the video Design WhatsApp w/ an Ex-Meta Senior Manager: System Design Interview breakdown. Read in order: requirements → entities → API → working high-level design → deep dives (scaling, inter-server routing, storage purge, extensions). Each HLD step is an improvement of the previous drawing — one requirement at a time — and every deep dive compares alternative components with their trade-offs before picking one.

Delivery framework (identical to Top-K, Ticketmaster & Uber — reuse it every time)

  1. Requirements (~5 min) — functional (what) + non-functional (how well). 4 small FRs, quantified NFRs.
  2. Core entities (~2-4 min) — User, Chat, ChatParticipant, Message, Inbox. Bullet each; fill the schema later.
  3. API (~5 min) — pick the transport first (WebSockets), then name the commands.
  4. High-level design (~10-15 min) — simplest system satisfying the functional reqs. Deliberately imperfect.
  5. Deep dives — return to the NFR list and fix what's missing. One deep dive per NFR.
Golden rule from the video: improve the design ONE problem at a time instead of jumping straight to the optimal system — you can't lose track of the functional requirements, and the interviewer watches you derive the design instead of reciting one.
  • FR1 — start group chats: anyone can create a chat with a list of users. A group of two IS a 1:1 chat — one entity, no special-casing DM vs group.
  • FR2 — send + receive messages: send once → it fans out to every member; whenever another member sends, you receive. The natural interviewer question — do we support video/audio/images? Yes — that becomes FR3.
  • FR3 — media attachments: images, video and audio live in messages; uploads can be hundreds of MB. This single requirement forces the S3 redesign (HLD v3).
  • FR4 — read messages after being offline: switch the phone off, come back, everything is there. Key insight from the video: a DEVICE goes offline, not a person — that is what creates the Client entity.
Keep it short: calling, presence, spam and scraping all sit in the out-of-scope box unless the interviewer pulls them in. The video's rule: if you're low on time, don't enumerate everything you're cutting — ask what the interviewer has in mind and move on.
  • NFR1 — low latency ≈ 500 ms delivery. Perceivable threshold: the difference between 100 ms and 500 ms is invisible in a chat app, so 500 ms is the real budget. This exact number comes back to pick the routing mechanism in deep dive 1b.
  • NFR2 — guaranteed delivery. "It would be weird if I sent a message and they said they never got it." Server-side persistence + client ACKs make delivery provable.
  • NFR3 — high throughput: billions of users. WhatsApp serves a couple of billion users; many messages per user per day. Defer the exact message count until the design needs it (≈100B/day in deep dive 2).
  • NFR4 — data is toxic sludge. Privacy: don't keep messages longer than needed; either delete them or encrypt them "so even you can't read them". Drives the 30-day purge service.
  • NFR5 — fault tolerance. At this scale components fail constantly; no single-server failure may take the app down.
CAP takeaway (say this unprompted): availability + eventual consistency for delivery (inbox retries until ACK), with exactness kept only for the tiny transaction window. Chat is the opposite shape from Ticketmaster's booking lock — worth saying out loud.
  • User — the only ACTOR, and all users are peers: no privileged actor. (Uber has riders/drivers, YouTube has creators/viewers; WhatsApp is flat.)
  • Chat — id, name, metadata. ONE entity for 1:1 and groups — an em-dash sized detail your interviewer will notice.
  • ChatParticipant — chatId + participantId. Composite PK answers "who's in this chat"; a Global Secondary Index on participantId answers "which chats am I in" — both lookups stay single-hop.
  • Message — id, contents, senderId, timestamp. The chat server stamps the time, not the client, so clocks stay consistent across senders.
  • Inbox — recipientId, messageId: one row per UNDELIVERED copy. This row is the entire delivery guarantee — delete-on-ACK makes retries free (HLD v4).
  • Client (device) — userId + clientId. Named here conceptually, promoted to a first-class key in the multi-device extension.
  • Reason to WebSockets in 3 steps (say them in order): ① latency-sensitive (500 ms) → no polling; ② frequent bidirectional traffic → no SSE (it's one-way); ③ no peer-to-peer or media-call requirement → no WebRTC. Persistent WebSocket/TLS connection it is. (Real WhatsApp uses a plain TLS connection — same principle, less overhead.)
  • Why not REST: half of chat traffic is server → client events; HTTP request/response only covers the client → server half. A RESTful API alone can't deliver a message.
  • Client → server commands: create_chat · send_message · create_attachment · modify_participants.
  • Server → client pushes: new_message · chat_created · participants_changed.
  • Iterate out loud: "this is just the scaffolding — I'll refine it as the design firms up." Never leave an obvious mistake sitting unacknowledged: the interviewer will assume you missed it even if you didn't.
  • Single chat server on purpose: the video's discipline — build the simplest thing that satisfies the FR, then evolve it. Jumping straight to a distributed system leaves gaps AND loses the interviewer's thread.
  • DynamoDB, or any KV store: reads are pure key lookups. SQL also scales (the video calls out Shopify's MySQL Black Friday numbers) — pick one and justify it out loud.
  • Two queries, two index shapes: composite PK on (chatId, participantId) → "members of chat X" · GSI on participantId → "chats I'm in".
  • Why it works: with ONE server every socket is local — the fan-out is a loop over a hashmap. A live chat room with sub-second delivery.
  • Why it's broken (say it yourself before the interviewer does): zero durability — a user not connected at send time sees nothing. NFR2 (guaranteed delivery) fails and FR4 (offline reads) is impossible.
  • Media doesn't fit either: a 500 MB video as a message would saturate the same pipe. → v3 swaps the media path, v4 adds durability.
  • Why the naive version dies (two reasons, say both): ① DynamoDB is a row store, not a blob store — videos are hundreds of MB; ② the chat server saturates on gigabyte uploads while its real job is shuttling kilobyte messages — the payload disparity is the smell.
  • Pre-signed URL flow: ① client asks the chat server for an upload target → ② chat server (authenticated) gets an S3 URL with embedded auth + TTL (~1 h) → ③ client uploads DIRECTLY to S3 → ④ the message body now carries the URL → ⑤ recipients fetch from S3 when rendering.
  • Expiry or it becomes a free Google Drive: purge media after every recipient has fetched it, with a ~30-day ceiling that also aligns with NFR4.
  • Guaranteed eventual delivery: a row survives until the client ACKs each message. Offline user reconnects → server drains their un-acked inbox → delivers → ACKs → deletes. NFR2 is now satisfied.
  • The 100-record transaction cap: DynamoDB transactions support ~100 records — message row plus one inbox row per member ⇒ group chats cap at ~100 members. Name this constraint before the interviewer does.
  • Checkpoint out loud: all 4 FRs plus NFR1 (500 ms push) and NFR2 (durable) hold on ONE node — "and I know exactly where it breaks: billions of users." → deep dives.
  • How the deep dives upgrade this drawing: deep dive 1 replaces "one chat server" with the L4 LB + pool and adds Redis Pub/Sub for the routing problem; deep dive 2 adds S3 (media offload) and the cleanup service (30-day purge). Everything else — the websocket hashmap, messages + inbox, ACK-deletes-row — was already there from HLD v2–v4.
  • The four flows you narrate from this one board: ① send = transaction + push (local socket or Redis route) + ACK cleans up · ② offline = drain inbox on reconnect · ③ media = pre-signed URL → direct S3 upload → URL in message · ④ purge = cron deletes past 30 days.
  • Whiteboard tip: draw v1 first, and show this board in the last five minutes — it's the "final answer" picture an interviewer wants to see once, whole: every requirement traced to a component.
  • Layer-7 HTTP LB doesn't work here: web servers are stateless, so an HTTP LB can terminate a request and forward it to ANY server. A websocket is a live connection — you cannot forward "the rest of it" to a different box mid-stream.
  • Layer-4 TCP LB does: the LB holds a symmetric TCP pair (client ↔ LB ↔ server), invisible to both ends — "as if the client connected directly". Choose servers by LEAST CONNECTIONS, because the connection IS the scarce resource; a fresh server saturates fast, which makes rollouts smooth.
  • The routing problem (the heart of this interview): A is on server 1, B is on server 2. A sends → S1 looks up participants ✓ and writes message + inbox ✓ — but B's socket lives on S2, so S1 cannot push. The chat servers need a way to hand messages to whichever server owns the recipient's websocket.
  • Kafka — the tempting first instinct, and why it loses: topics-per-user sounds clean, but each topic costs ~50–100 KB of overhead — billions of users ⇒ terabytes of metadata just to exist — and Kafka isn't built for the short-lived, churn-heavy topics a chat app creates on every connect/disconnect.
  • Consistent hashing — correct, expensive to operate: a chat registry + shared config (ZooKeeper/etcd) lets any server compute "user B ↦ server 2" and write directly (2 hops). But growing 4 → 5 servers moves ~20% of users: disconnect → re-register → reconnect, drained slowly, with double-sends in the window — plus the risk of hot servers.
  • Redis Pub/Sub — the winner: each chat server subscribes to the topics of the users it serves; a publish fans out to the owning server's socket. At-most-once delivery is FINE because the messages + inbox tables already guarantee delivery — pub/sub is only the <500 ms fast lane. Costs: n×m server↔node connections, and the same migration chore if the Redis cluster itself grows.
Say this sentence (it's the whole deep dive): "We keep the realtime path thin and lean on the durable store — worst case the message is already sitting in the inbox."
  • Messages: add a secondary index on the server-stamped timestamp → delete rows older than 30 days, no per-row bookkeeping.
  • Inbox: rows die on ACK (they ARE the delivery state); add a timestamp so stale undelivered rows get purged too. When the LAST inbox row for a message is deleted, delete the message row — every recipient already has it.
  • Race conditions don't matter: the 30-day guard rail absorbs them — worst case one extra copy exists for a day. This is what "data is toxic sludge" means in practice: delete early, or encrypt it "so even you can't access it" (Meta's liability framing, verbatim).
  • Multi-device: add Client (userId, clientId); re-key inbox rows and pub/sub topics from user → client; fan out per participant × per device. Row blow-up — 100 people × 5 devices = 500 rows > the 100-row transaction cap → cap devices at 2–3 and shrink group limits alongside.
  • Presence (green orbs): availability table (userId · status), flipped available/unavailable on connect/disconnect. Poll it for a cheap contact list, or subscribe watchers via the existing pub/sub for live updates. The hard part is fan-out again: one disconnect must not notify 10 000 watchers — product caps who watches whom.
  1. Requirements: FR1-4 (chats → messages → media → offline) · NFRs: 500 ms · guaranteed delivery · ~2B users · 30-day toxic-sludge purge · fault tolerance.
  2. Entities: User (peers) · Chat · ChatParticipant · Message · Inbox (+ Client for devices). The inbox row-per-recipient IS the delivery guarantee.
  3. API: WebSockets (latency ⇒ no polling · bidirectional ⇒ no SSE · no P2P ⇒ WebRTC out). Commands, not REST.
  4. HLD evolution: v1 single node + chat tables → v2 + connection hashmap → v3 swap blobs for S3 pre-signed URLs → v4 + messages/inbox transactions (group ≤ 100).
  5. Deep dive 1 (scale): L4 TCP LB + least-connections → the routing problem. Options: Kafka ✗ → consistent hash ~ → Redis Pub/Sub ✓ over the durable store.
  6. Deep dive 2 (data): 100 TB/day math → few hundred TB live · cleanup service enforces 30 days · delete-on-ACK + last-row-deletes-message.
  7. Extensions: multi-device = re-key everything to Client · presence = status table + pub/sub, capped fan-out.
